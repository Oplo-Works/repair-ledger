## 확정 범위 (v2)
- 플랫폼: Web / Chrome Desktop 단일.
- 입력: 영어 텍스트 메모만. OCR·사진 분석·음성 제외.
- 하자 유형 4종 (난방·누수·곰팡이·해충) + **"분류 불가/검토 필요" 상태 허용** (강제 분류 금지).
- 날짜·위치: UI 입력/코드 파싱이 기본. Nano 추출은 Day-1 벤치마크에서 정확도가 확인되면 보조로 채택.
- 한국어: 안내 UI 유지, 서한 해설은 동적 생성이 아닌 고정 안내문.
- 타임라인은 앱 코드 정렬 (클라우드 생성 아님). 311/HPD는 공식 출처·확인일 표기한 정적 체크리스트 + 법률자문 아님 고지.
- 수정 이력 UI 없음. AI 원출력과 사용자 확정본 2개 버전만 보존.
- 필수 포함: 기록 삭제 기능, 서한 복사(내보내기), 샘플 데이터 로더(합성 표기), 지원 안 함 환경 안내 화면.

## 데이터 경계 (명문화 — 과장 금지)
세 가지를 분리해서 설계하고 README·제출 문안에 그대로 공개한다:
1. 로컬 추론에 들어가는 데이터 (기기 안)
2. 저장·동기화를 위해 Firebase로 보내는 데이터 (원문 포함 — "원문이 기기를 안 떠난다"고 쓰지 않는다)
3. 서한 합성을 위해 클라우드로 보내는 데이터 — 전송 전에 범위 미리보기 + 사용자 동의 화면 필수.
- 상태 머신: Draft → Processing → Needs Review → Confirmed → Included in Letter. 처리 실패해도 원문은 Needs Review로 보존.
- 원문을 수정하면 기존 AI 제안의 확인은 무효화된다. **기록을 수정·삭제하면 그 기록을 인용한 서한은 무효화되고 재생성해야 한다** (버전 스냅샷 보존 방식은 이 일정에서 채택하지 않음 — 최종 검증에서 확정된 해법).
- 저장 경로는 **Firestore 오프라인 영속성 단일 경로**로 확정. 자체 동기화 엔진·서비스워커는 만들지 않는다 (Firestore 영속성 자체가 IndexedDB 기반 — 이중화는 과잉 설계). 저장 상태는 4단계로 표시: 기기 반영 / 동기화 대기 / 서버 반영 / 동기화 실패. 저장 완료 대기로 화면을 막지 않는다.
- 동의는 두 번, 순서가 있다: (1) 저장 시점 — 원문이 Firestore에 동기화된다는 고지·동의 (재연결 시 자동 전송되므로 최초 외부 전송은 저장이 먼저다). (2) 합성 시점 — "선택한 기록을 Gemini 합성에 전송" 별도 버튼·별도 동의 + 전송 범위 미리보기.
- 접근 통제: 익명 Auth + uid 기준 Firestore Security Rules (타인 기록 읽기·수정·삭제 차단). 실제 본인 기록을 넣기 전에 규칙을 테스트로 검증한다. App Check는 소유권 검증을 대신하지 않는다.
- 오프라인 흐름: 입력 → 로컬 추론 → 확인 → Firestore 영속 캐시(기기 내) → 재연결 시 자동 동기화. 중복 방지 ID 포함. 오프라인 새로고침 시 페이지 재로딩은 보장 범위 밖 (데모는 새로고침 없이 진행).

## 아키텍처 원칙 (v2)
- 로컬 단계 ONLY_ON_DEVICE 강제. 불가 시 명시 고지, 조용한 fallback 금지 — 이 차단을 테스트 케이스로 검증.
- Day-1 성공 기준은 availability() 값이 아니라 **실제 Firebase SDK 호출 성공 + inferenceSource === ON_DEVICE 확인**. 직접 Prompt API 호출은 진단용으로만.
- 모든 AI 호출에 inferenceSource 배지 (요청 모드가 아닌 실제 응답값 기반) + 처리 시간 표시.
- 모델 생애주기 UI가 첫 화면: 미준비 → 사용자 클릭으로 initializeDeviceModel() → 다운로드 진행 → 준비 완료. 모델 미준비 상태 처리는 Phase 1 항목.
- 클라우드 서한은 구조화 출력으로 받는다: 문장 배열 {text, sourceRecordIds[]}. 앱이 모든 ID의 존재와 확인 상태를 검증하고, 무효하면 서한 생성을 실패로 처리. 법 조항은 모델이 쓰지 못하게 하고 정적 허용 목록만.
- App Check: 프로덕션 attestation을 배포 도메인 + 디버그 토큰 없는 새 프로필에서 성공하는 것까지가 "구성 완료". 디버그 토큰·키는 공개 레포에 절대 포함 금지.
- SDK 버전 고정 (package lockfile), 제출일까지 무단 업그레이드 금지. 검증한 Chrome 버전·환경을 기록.

## Day-1 게이트 (11/15 밤 — 통과 기준은 수직 흐름 완주)
최종 검증 3개의 수렴 지적: 게이트 항목 9개를 첫 주말에 다 통과시키는 건 과부하이고, 오프라인 저장·클라우드 합성은 11/16–19에 완성될 기능에 의존해 순서가 역전돼 있다. 그래서 게이트를 둘로 나눈다.

**필수 게이트 (11/15 밤까지, 이게 통과 못 하면 일정이 아니라 기술 재평가):**
0. Devpost Rules 원문 직접 확인 (레포·라이선스·영상·제출 항목 대조).
1. 모델 다운로드를 가장 먼저 시작. Firebase SDK로 ONLY_ON_DEVICE 실호출 + inferenceSource === ON_DEVICE 확인.
2. **배포 URL에서 수직 흐름 완주**: 로컬 1회 → 확인·저장 → 클라우드 1회 → 인용 역추적까지 한 흐름으로. 골격+별도 스파이크 수준은 통과가 아니다.
3. App Check 프로덕션 검증 (배포 도메인, 새 프로필, 시크릿 창). AI Logic enforcement 상태 콘솔에서 직접 확인.
4. 클린 프로필 기준 분리: 지원 설정(플래그 등 공식 절차)에서는 로컬 실행 성공이 기준이고, 플래그 없는 환경에서는 "정확한 미지원 안내가 뜨는 것"이 성공 기준이다. 둘을 섞지 않는다.
5. 최소 오프라인 실험 1건: 모델 준비 후 네트워크 차단 → 추론 → (새로고침 없이) 저장 상태 표시까지.
6. 사용할 클라우드 모델 명시 지정 + 합성 1회로 모델 동작·ID 계약 확인 (기본 경량 모델에 맡기지 않음).

**이월 항목 (핵심 흐름 통과 후 11/16–19에 실시):**
7. 모델 생애주기 세부: 다운로드 소요 시간, 재시작 후 유지, 미지원 환경 안내.
8. 오프라인 세부: 재연결 동기화, 저장 상태 4단계 전이 확인.
9. 품질·지연 벤치마크 본편: 영어 메모 10건 (날짜 미상, 복수 하자, 범위 밖 입력, 오타·속어, 지시문 형태 메모 혼합). 스키마 2안 비교. 콜드·웜 분리, 평균·중앙값·최댓값. **실패 케이스 전부 보관**.
10. 클라우드 합성 측정 본편: 가짜 기록 10건으로 지연·ID 오류율.
11. 한국어 입력 반응 확인 (5분): 예외인지 환각 출력인지, 앱 차단 방식 확정용.

### 분기표 (게이트 판정표 — 미리 구현하는 목록이 아니다)
분기 경로는 각각 별도 파이프라인+UI이므로, 전부 미리 만들지 않는다. 게이트 실측 결과로 경로 하나만 선택해 구현한다.
- 지연 ≤5초: 현 설계 유지. 5–10초: 진행 상태 UI 강화 후 진행. 10–20초: 재작성을 분리하거나 결정적 템플릿으로 대체. >20초: 분류+최소 필드만 Nano. 30초 초과 반복: 재판정.
- Nano가 실제로 실행 안 됨: 지연 분기표로 넘길 문제가 아니다. UI 개발 중단, 환경·SDK 경로 해결 우선. 11/15까지 해결 안 되면 완성품 제출 가능성을 재평가 (STOP 게이트, 명시).
- 형식 실패·중대 사실 추가가 10건 중 2건 이상: 입력·필드 축소 후 재시험. 자동 재시도로 덮지 않는다.
- 오프라인에서 SDK 실패: 오프라인 장면을 재설계하거나 삭제.
- App Check 배포 실패 반복: 기능 확장 중단, provider·도메인·초기화 순서부터 해결.
